# islo release versions

- Development branches use three components, for example `26.4.3` or `26.4.4`.
- Public release versions use four components. The first release on `26.4.3` is `26.4.3.1`, followed by `26.4.3.2`, and so on. On a new `26.4.4` branch, start again at `26.4.4.1`.
- `VERSION` is the public version source. Start at `.1` on a new branch; when the current version has already been released, increment its fourth component for the next release. Do not replace an existing release or move its tag.
- Cargo requires three-component SemVer. Keep `Cargo.toml` and the root package in `Cargo.lock` equal to the branch prefix, while application UI, update checks, Windows resources and package filenames use `VERSION` via `ISLO_APP_VERSION`.
- Run update-version tests and the native installer/updater fixtures for both three- and four-component versions when changing release plumbing.

## Entry points and Agent control

- Keep one Cargo package with the desktop entry in `src/main.rs`, CLI entry in `cli/src/main.rs`, shared settings in `src/model.rs`, and local command transport in `src/agent_control.rs`.
- CLI and agent settings changes must reuse model validation and persistence. A running GUI owns mutations; do not overwrite its settings file behind its back.
- For operating the local application's settings, read `skills/islo-control/SKILL.md` and use `islo-cli`. Account secrets and system autostart are outside this settings interface.
- Domain commands live in `src/agent_commands.rs`; CLI parsing and `capabilities` share one command table. Reuse model validation/persistence; save successfully before replacing live memory. Queries must whitelist output fields and omit credentials and message secrets.
- CLI must be enabled from Settings → General. Registration adds only the installation directory to per-user PATH; removal must preserve unrelated/pre-existing PATH entries. Keep installer/uninstaller cleanup in sync.
- For tasks, reminders, calendar, focus, water, shelf, media and status queries, read the same `islo-control` skill. Run `capabilities` before assuming a command exists. Task references are snapshots; re-list after mutations. A timeout means outcome unknown, so query before retrying a write.
- All Agent/CLI configuration follows one interaction contract: ordinary metadata is supplied through commands; missing ordinary fields return requirements/validation errors for the Agent to resolve, never a configuration window. Only a needed password, authorization code, API key, token or similar secret may open a compact local prompt containing its purpose/destination, one masked field, and cancel/confirm. Existing credentials are reused. Unsupported secret configuration must be reported as unsupported, never worked around through chat or raw credential-store writes.
- Every secret-capable domain must reuse `src/agent_input.rs` for rendering and clipboard capture reservation/release, and its existing native credential storage. Keep values out of CLI arguments, stdin, IPC JSON, results and logs. Pair release with save, cancel, expiry and interface disable; clear temporary values, return status only, and preserve live/disk state when cancelled or failed. Do not inspect real input windows, screenshots or clipboard to obtain values.
- Mail account configuration uses `mail configure` and the shared secret prompt. `needs_metadata` opens no window; `awaiting_input` includes a request ID for `mail input-status` / `mail input-cancel`. `saved` confirms persistence; check `mail status` separately for connection. This explicitly requested flow extends account configuration beyond the original settings-only interface.
- Provider OAuth is an alternative to secret entry: Outlook uses Microsoft browser consent, PKCE and a local callback; only request status reaches the Agent. Never inspect login pages/callback URLs or reuse another product's client ID. Keep the product's public `outlook_client_id` in normal settings or `ISLO_OUTLOOK_CLIENT_ID` for release builds; refresh tokens stay in native credentials. Registration and verification requirements are documented in `docs/OUTLOOK.md`.
